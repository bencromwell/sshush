# Agent Instructions for sshush

This file contains instructions for AI agents working on the sshush project.

## Requirements

### Code Quality

**All commits must pass the project linter.**

Before committing any changes, run:
```bash
make lint
```

The linter enforces:
- Code formatting (`go fmt`)
- Linting (`golangci-lint`)
- Consistent style across the codebase

### Testing

**All commits must maintain or improve test coverage.**

Before committing:
```bash
# Run all tests
go test ./...

# Check coverage
go test ./... -coverprofile=coverage.out
```

### Commit Messages

**Commit messages must follow conventional commit style:**

```
<type>(<scope>): <description>

<optional body>

<optional footer>
```

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`

Example:
```
test(cmd): add integration tests for CLI functions

Add tests for NewRootCommand and expandPath/expandGlobs:
- Test command metadata and flag registration
- Test path expansion with tilde, env vars, braces
- Test glob pattern matching

Coverage: cmd package 26.9% -> 86.5%

Generated by Mistral Vibe.
Co-Authored-By: Mistral Vibe <vibe@mistral.ai>
```

## Project Structure

- `docs/` - Documentation
- `AGENTS.md` - This file

## Specific Guidelines

### Test Files

1. **Location**: Place test files alongside the code they test (e.g., `cmd_test.go` in `cmd/`)
2. **Naming**: User `_test.go` suffix
3. **Organization**: Group related tests with `t.Run()`
4. **Golden files**: Store in `testdata/` subdirectories

### Test Data

- Use temporary directories (`t.TempDir()`) for file operations
- Clean up after tests
- Use realistic but minimal test data

### Code Changes

1. **Before modifying**: Read the existing code thoroughly
2. **Style**: Match the existing code style
3. **Scope**: Make minimal, focused changes
4. **Effects**: Run tests to ensure no regressions

## Workflow

1. **Read**: Understand the existing codebase and AGENTS.md
2. **Plan**: Outline changes before implementing
3. **Implement**: Make changes incrementally
4. **Lint**: Run `make lint` to catch issues early
5. **Test**: Run `go test ./...` to verify behavior
6. **Commit**: Create descriptive, well-formatted commit messages

## CI/CD

The project uses GitHub Actions for CI. Key workflows:
- **Lint**: Runs `make lint` on all PRs
- **Test**: Runs `go test ./...` on all PRs
- **Build**: Builds binaries for releases
- **Release**: Runs [semantic-release](https://semantic-release.gitbook.io/semantic-release/) on every push to `main`. It analyses conventional commits, determines the next version, and cuts a GitHub release; GoReleaser then builds and attaches the binaries. Pushing a `v*` tag manually still triggers GoReleaser directly.

Because releases are driven by commit messages, [conventional commit style](#commit-messages) is required not just stylistically but functionally. Every commit type is release-eligible: `feat:` cuts a minor, `BREAKING CHANGE:` (or `!`) a major, and every other type — `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `style:`, `ci:`, `build:` — cuts a patch release, so a push to `main` always produces a release (unless the commit list is empty).

All PRs must pass CI checks before merging.
